# Аудит структуры и реализации vysh

Дата: 13 октября 2026 года. Проверенная версия: `0.4.3+54`, коммит `7c81f44`.

Проект имеет подходящий фундамент: UI разложен по функциям, SSH и SFTP имеют интерфейсы, секреты отделены от JSON, платформенный код собран отдельно. Главная проблема — разделение каталогов пока не обеспечивает разделение ответственности. Домен напрямую создаёт инфраструктуру, сессия управляет одновременно соединением, терминалом, аутентификацией и локальным редактированием, а обработка ошибок часто скрывает неудачные операции.

Первый приоритет — исправить сохранение данных, SFTP и жизненный цикл соединения. Затем стоит уточнить границы слоёв и разделить крупные классы. Полное переписывание приложения для этого не требуется.

## Рекомендуемая организация каталогов

Сохранить нынешнее разделение и доработать его постепенно:

```text
lib/
  app/
    bootstrap.dart
    dependencies.dart        # конкретные реализации портов и providers
    controllers/             # координация сессий, настроек, вкладок
    terminal/                # xterm bridge, если не вводить TerminalEngine
  domain/
    models/                  # независимые модели данных
    ports/                   # SSH, SFTP, secrets, repositories
    services/                # политики подключения/передач
  infra/
    ssh/
    storage/
    secrets/
    platform/
  ui/
    hosts/
    terminal/
    sftp/
    settings/
    shell/
    theme/
    widgets/
  l10n/
test/
  domain/
  infra/
  ui/
  support/
integration_test/
```

Не переносить всё одним большим изменением. Сначала определить интерфейсы и владельцев ресурсов, затем переносить по одному модулю с сохранением поведения и подходящими тестами. Отдельные Dart-пакеты для каждого слоя пока добавят больше обслуживания, чем пользы; запрет нежелательных imports можно начать с простой проверки в CI.

## Обзор по разделам репозитория

| Раздел | Оценка и действие |
|---|---|
| `lib/app`, `main.dart` | Хорошая точка сборки приложения; перенести туда DI и явно описать bootstrap/ошибки startup |
| `lib/domain/models` | Host достаточно прост; вынести локализацию и Flutter theme-модели, добавить безопасное декодирование |
| `lib/domain/ports` | Хорошая основа; добавить отмену, typed SFTP errors и интерфейсы хранения |
| `lib/domain/services` | Самое важное место рефакторинга: ответственность, generation, persistence и ресурсы |
| `lib/infra/ssh` | SSH адаптер изолирован; исправить F02, F06, F19, F20 |
| `lib/infra/storage`, `secrets` | Улучшить подтверждение операций, восстановление и диагностируемость |
| `lib/infra/platform` | Уточнить возможности и типы путей; сократить повторные static/global зависимости |
| `lib/ui/hosts` | Разделить форму/сохранение и массовые действия; тестировать после await и пустой список |
| `lib/ui/terminal` | Уменьшить монолит, изолировать renderer/gestures, исправить F18 и семантику editing |
| `lib/ui/sftp` | Контроллер каталога, typed actions, локализация и корректные права |
| `lib/ui/settings`, `theme` | Общие виджеты уже выделены; унифицировать строки и настройки для платформ |
| `lib/ui/shell` | Сохранение вкладок разумно; добавить очистку UI-состояния и lifecycle-проверки |
| `android` | Разделить Activity channels, downloads и service; проверить F10–F12 на устройстве |
| `windows`, `linux` | Стандартные runner-шаблоны; синхронизировать startup config с Dart |
| `test` | Хорошая начальная база, но недостаточный охват рисков основных функций |
| `.github/workflows` | Уравнять SDK, добавить release gates и проверку версии |
| `tools/release`, `packaging` | Версия/sha256 автоматизированы; добавить проверки сценариев prerelease/нет артефакта и точные метаданные |
| `tools/demo` | Полезный изолированный стенд; сделать основой integration-тестов, добавить симметричную Linux-команду остановки |
| `themes/templates` | Готовые адаптеры полезны; добавить fixtures разборов и проверку шаблонов генераторами |
| `assets` | В основном иконки; если встроенный шрифт остаётся требованием, включить ресурс и лицензии |
| `third_party/xterm2` | Небольшой документированный patch; добавить воспроизводимость и отдельную проверку |
| `docs`, `README`, `CHANGELOG` | Полезная документация; отделить планы от реализованного и синхронизировать темы/SDK/возможности |
| `.gitignore`, `.gitattributes` | Правильно исключают сборки/секреты и задают окончания строк; генерируемые каталоги не нужно включать в аудит исходников |

## Порядок работ

1. **Надёжность и данные:** F01–F05, F07, F18; добавить регрессионные проверки по подтверждённым сценариям.
2. **Передачи и платформы:** F06, F08–F14, F16–F20; проверить отмену, конфликты, Android Download и background lifecycle.
3. **Небольшие точечные исправления:** F15, F17, согласование renderer/профиля и IPv4/IPv6.
4. **Структура:** R01–R06 по одному модулю; UI и storage проверять после каждого переноса.
5. **Разработка и сопровождение:** R07–R12 — CI, документация, локализация, fork и измерение производительности.

Исправления поведения целесообразно делать небольшими отдельными изменениями. Большой рефакторинг до устранения подтверждённых ошибок усложнит проверку и перенесёт существующие дефекты в новые каталоги.
